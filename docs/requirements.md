# power-manager 要件定義

本書は「何を実現するか（WHAT / WHY）」を定義する。実現手段（HOW）は [アーキテクチャ設計](architecture.md)、セキュリティの実装方針は [セキュリティ設計](security.md)、設定・配備・運用は [運用設計](operations.md) に記す。

要件 ID は他ドキュメントから参照する。変更時は ID を維持し、削除した場合は欠番とする。

## 1. 目的

自宅ホームラボのサーバーを、外出先からでもブラウザだけで起動・停止・状態確認できるようにする。そのために、家庭内 LAN に常駐する小さな管理アプリケーションを用意する。

## 2. 完成像

利用者が VPN 経由で管理画面を開くと、登録済みサーバーの一覧と現在の稼働状態が表示される。各行のボタンで起動または停止を指示でき、結果がその場で分かる。画面を開いたままでも状態表示は自動で更新され、管理対象を追加・変更したときは再起動せずに設定を反映できる。

管理アプリケーション自体は状態を持たず、壊れても作り直せる。秘密情報はアプリケーションの設定ファイルに置かず、配備側の秘密管理から渡す。管理画面は VPN と TLS の内側にのみ置き、インターネットへ直接公開しない。

## 3. 利用者と利用シーン

- 利用者はホームラボの管理者本人 1 名のみ。
- 主な利用シーンは、外出先から VPN 経由でアクセスし、NAS や検証機の電源を入れる／切る、稼働状態を確認する、という操作である。
- 家庭内 LAN からアクセスする場合も同じ画面を使う。

## 4. スコープ

### 4.1 初回版で提供する機能

- 登録済みサーバーの一覧表示と死活状態の表示
- Wake-on-LAN による対象サーバーの起動
- 対象サーバー上での停止コマンド実行
- 設定した接続先ポートへの TCP 接続による死活確認
- 管理対象定義の検証付き再読込
- 操作の成功・失敗表示
- 管理画面全体の認証

### 4.2 初回版の対象外

- 再起動、強制停止、複数台の一括操作
- 予約実行・スケジュール
- 永続的な操作履歴・監査証跡
- 外部自動化向けの公開 API
- 利用者ごとの権限管理、複数アカウント
- アプリケーション独自のログアウト機能

## 5. 機能要件

### FR-01 サーバー一覧

登録済みの全サーバーについて、表示名と死活状態を 1 画面に一覧表示できること。登録順序は設定ファイルの順序に従う。

### FR-02 死活状態の自動更新

- 画面の初期表示時に死活状態を取得して表示すること。
- 画面を開いたままでも、状態表示が自動で更新されること。更新間隔は 15 秒とする。
- 手動更新（ブラウザの再読み込み）でも同じ死活確認が行われること。
- 自動更新は状態表示の領域のみを差し替え、画面全体の再読み込みや入力中の操作状態の破棄を起こさないこと。
- 自動更新は追加の操作を要求しないこと。

### FR-03 死活状態の表現

死活状態は次の 3 値で表現すること。

| 状態      | 意味                                               |
| --------- | -------------------------------------------------- |
| `online`  | 設定した接続先ポートへの TCP 接続に成功した        |
| `offline` | 接続に失敗した、または規定時間内に結果が出なかった |
| `unknown` | まだ確認結果がない                                 |

ICMP ping の応答やログイン成功の有無は判定条件に含めない。

### FR-04 起動（Wake-on-LAN）

- サーバーを 1 台指定して起動を指示できること。
- 起動指示の成功条件は、起動要求パケットの送信が成功したこととする。OS の起動完了は待たない。
- 起動完了の確認は利用者が死活状態の変化で行う。

### FR-05 停止

- サーバーを 1 台指定して停止を指示できること。
- 停止指示の成功条件は、対象サーバー上の停止コマンドが正常終了したこととする。
- 停止の実行前に、利用者へ確認を求めること（誤クリック防止）。
- 停止コマンドは対象サーバー側でパスワード入力なしに実行できる範囲に限定すること。

### FR-06 操作の排他

同一サーバーに対して電源操作（起動・停止）が実行中のとき、新たな電源操作を受け付けず、実行中であることを利用者に表示すること。排他の状態はアプリケーションの再起動で消えてよい。

### FR-07 操作結果の表示

- 操作後は一覧画面へ戻り、操作の結果を表示すること。
- 表示する結果は「成功」「失敗」「実行中（拒否）」の別と、対象サーバーの識別子に限る。
- コマンド内容、認証情報、鍵情報、内部エラーの詳細を画面に表示しないこと。
- 結果表示は再読み込みや URL 共有で操作が再実行されない形であること。
- 設定再読込の失敗もこの表示範囲に従う（結果種別のみを表示し、失敗理由はログにのみ記録する）。

### FR-08 設定の再読込

- 稼働中に管理対象の定義を再読込できること。アプリケーションの再起動を要求しない。
- 再読込する定義は、反映前に全体を検証すること。1 件でも不正があれば反映しない。
- 検証に失敗した場合は、直前の有効な定義を維持し、失敗したこと（結果種別）を画面に示すこと。失敗理由はログにのみ記録し、画面には出さないこと（FR-07 の表示範囲に従う）。
- 起動時の定義検証に失敗した場合は、画面を提供せずに起動を中止すること。

### FR-09 設定の検証

管理対象の定義について、少なくとも次を検出して拒否すること。

- 形式のバージョン情報の欠落・不一致
- 未知の項目、型の不一致、必須項目の空値
- 識別子の重複
- 不正な MAC アドレス
- 範囲外のポート番号

### FR-10 認証

- 管理画面のすべての画面とすべての操作が認証を要求すること。
- 未認証の要求は拒否し、認証を促す応答を返すこと。
- 認証に成功した利用者は、追加のログイン操作なしに各画面を利用できること。

## 6. 非機能要件

### NFR-01 単一利用者

利用者は本人 1 名とし、利用者ごとの権限管理は提供しない。

### NFR-02 無状態性

- アプリケーションは永続状態を持たないこと。データベース、独自の一時ファイル、操作履歴ファイルを作成しない。
- プロセスを再起動したとき、設定ファイルと環境変数のみから同じ動作を再現できること。
- 実行中に保持する状態（排他ロック、進行中の確認）はメモリ上のみでよい。

### NFR-03 配布形態

- ホストへ配備する成果物は単一の実行可能ファイルとして提供できること。
- 宣言的な構成管理から配備でき、バージョン固定とロールバックが可能であること。
- `x86_64-linux` と `aarch64-linux` の両方で動作すること。

### NFR-04 待受と公開範囲

- アプリケーションはホストの loopback でのみ待ち受けること。
- TLS 終端と外部からの受信は既存のリバースプロキシに委ねること。
- アプリケーションを直接インターネットへ公開しないこと。

### NFR-05 常駐性と障害時の挙動

- ホストのサービス管理機構により常駐し、ホスト起動時に自動で開始すること。
- 予期しない異常終了時は自動再起動されること。
- 設定不備による終了では再起動を繰り返さないこと（再起動ループの防止）。

### NFR-06 起動時の検証

必須の実行時設定がすべて存在し妥当でなければ、待受を開始せずに起動を中止すること。CLI 引数による設定は受け付けない。

### NFR-07 応答時間の上限

各操作は有限時間で結果を返すこと。上限は次のとおり。

| 操作             | 上限  |
| ---------------- | ----- |
| 死活確認（1 台） | 5 秒  |
| 起動要求の送信   | 5 秒  |
| 停止コマンド実行 | 30 秒 |

### NFR-08 対象数増加への耐性

- 死活確認の同時実行数を有限の範囲に保つこと。
- 複数の画面、手動更新、自動更新が重なっても、同一対象への確認を重複して実行しないこと。
- 1 回の確認に時間がかかり自動更新の間隔を超えても、未完了の確認を次回以降に重複して起動しないこと。

### NFR-09 プログレッシブな操作性

自動更新にのみブラウザ側のスクリプトを使用し、一覧表示・起動・停止・設定再読込は通常のフォーム操作で成立すること。ブラウザ側スクリプトが無効でも自動更新以外は利用できること。

### NFR-10 可観測性

- ログはファイルへ書かず、標準出力・標準エラーへ構造化形式で出すこと。
- ログの保持はホストのログ収集機構に委ねること。
- 対象サーバー ID、操作種別、成功・失敗、失敗分類を記録できること。

### NFR-11 保守性

- 要件（本書）、アーキテクチャ、セキュリティ、運用の各ドキュメントを分離し、技術選定の見直しが要件定義に影響しない構成とすること。
- 自動テストにより、設定検証・認証・操作ルーティング・外部コマンド組立て・排他制御を検証できること。

## 7. セキュリティ要件

詳細な実装方針は [セキュリティ設計](security.md) を参照する。

- **SEC-01** 管理画面のすべての画面と操作に認証を要求すること。
- **SEC-02** 通信は TLS で保護し、アプリケーションは loopback でのみ待ち受けること。
- **SEC-03** 状態を変更する操作は、意図した画面からの要求であることを検証すること（CSRF 対策）。
- **SEC-04** 秘密情報（認証情報、秘密鍵など）を管理対象の定義ファイルに含めないこと。秘密情報は配備側の秘密管理から実行時に渡すこと。
- **SEC-05** 秘密情報を画面表示およびログに出さないこと。パスワードは復元不可能なハッシュとして保持すること。
- **SEC-06** 停止操作に使う認証情報は、対象サーバー上で必要最小限の権限に限定すること。
- **SEC-07** 停止という破壊的操作の前に、利用者へ明示的な確認を求めること。
- **SEC-08** アプリケーションの実行プロセスは、専用の非特権ユーザーで動作し、不要な権限・ファイルシステム・ネットワーク機能を持たないこと。
- **SEC-09** 将来、秘密管理の方式を変更しても、アプリケーション側の受け取り方法を変えずに済むこと。

## 8. 制約と前提

- **CON-01** 管理対象は家庭内 LAN 上にあり、起動要求（ブロードキャスト）が到達できること。
- **CON-02** 管理対象は、遠隔からの停止指示を受け付けて停止コマンドを実行できる手段を提供していること。
- **CON-03** 管理対象の MAC アドレスと接続先ホスト・ポートが既知であること。
- **CON-04** ホストは Linux で、常駐サービスを管理する仕組みを持ち、常時稼働していること。
- **CON-05** 外部からのアクセスは既存の VPN 経由であり、既存のリバースプロキシが TLS を終端できること。
- **CON-06** 秘密情報は、ホスト上の root 限定ファイル等の安全な場所から実行時に渡せること。
- **CON-07** 管理対象の定義は 1 個のファイルで管理し、その形式はバージョン識別子を持つこと。

## 9. 受け入れ基準

初回版は次を満たしたとき受け入れとする。

1. 認証なしでは一切の画面・操作にアクセスできない。
2. 一覧に登録済みサーバーが表示され、15 秒ごとに状態が更新される。
3. 起動操作で対象が起動し、状態が `online` に変わる。
4. 停止操作で確認を求められ、承諾すると対象が停止し、状態が `offline` に変わる。
5. 不正な設定を再読込しても旧設定で動作を継続し、失敗したこと（結果種別）が画面に表示され、失敗理由がログに記録される。
6. 不正な設定で起動した場合、待受を開始せずに終了し、再起動ループに入らない。
7. 同一サーバーへの二重操作が拒否され、その旨が表示される。
8. アプリケーションを再起動しても、設定ファイルと環境変数のみから同じ状態に復帰する。
9. VPN 外からは到達できず、VPN 内からは TLS 経由で利用できる。

実際の起動要求送信、SSH 接続、VPN・リバースプロキシ経由のアクセスは、ホームラボ上での手動受け入れテストで確認する（手順は [運用設計](operations.md)）。
