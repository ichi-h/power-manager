# power-manager アーキテクチャ設計

本書は「どう実現するか（HOW）」を定義する。目的・要件は [要件定義](requirements.md) を参照する。認証・秘密情報の詳細は [セキュリティ設計](security.md)、配備・設定ファイル・CI は [運用設計](operations.md) に記す。

要件 ID（`FR-*`、`NFR-*`、`SEC-*`、`CON-*`）は [要件定義](requirements.md) のものを指す。技術選定を変更する場合、本書のみを更新すればよく、要件定義は変更しない。

## 1. 技術選定

| 領域                | 採用技術                                                           | 主な根拠                                                                       | 関連要件               |
| ------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------ | ---------------------- |
| 実行環境            | Bun（TypeScript 直接実行）                                         | 単一バイナリへのコンパイル、HTTP/UDP/TCP/子プロセス/Argon2 を標準 API で賄える | NFR-03, NFR-07, SEC-05 |
| 言語                | TypeScript                                                         | 設定と外部入力を型で拘束できる                                                 | NFR-11                 |
| HTTP フレームワーク | Hono                                                               | 軽量、Fetch API ベースでルーティングとミドルウェアだけを提供                   | NFR-09                 |
| 画面                | サーバーサイドレンダリング + HTML フォーム（テンプレートリテラル） | 一覧・操作・再読込を素のフォームで成立させ、CSR と JSX 依存を不要にする        | NFR-09                 |
| 自動更新            | 素の `fetch` + 最小のインラインスクリプト                          | 状態表示の差し替えだけに限定し、フレームワークを追加しない                     | FR-02, NFR-08, NFR-09  |
| 入力検証            | Zod                                                                | スキーマによる厳格な検証（未知項目の拒否を含む）                               | FR-09                  |
| 設定形式            | JSON（ルートに `version`）                                         | コメント不要の単純なデータ、宣言的配備との相性                                 | CON-07, FR-09          |
| 起動要求            | UDP ブロードキャスト（Magic Packet）                               | 標準的で対象側に追加ソフト不要                                                 | FR-04                  |
| 停止                | OpenSSH クライアントを子プロセス実行                               | 対象側に常駐エージェントを置かず、既存の SSH 基盤を使う                        | FR-05, SEC-06          |
| 死活確認            | TCP 接続（設定済みホスト・ポート）                                 | ICMP 権限やログイン認証を必要とせず、停止コマンド経路と同じ到達性を見られる    | FR-03                  |
| 認証                | HTTP Basic + Argon2id                                              | 単一利用者に対して実装が最小。ハッシュは配備側で生成                           | FR-10, SEC-05          |
| 配布                | Nix flake + NixOS モジュール                                       | バージョン固定、ロールバック、systemd 連携                                     | NFR-03, NFR-05, CON-04 |
| CI                  | GitHub Actions                                                     | PR と main で型検査・テスト・Nix ビルドを検証                          | NFR-11                 |

### 1.1 不採用とした選択肢

| 選択肢                         | 不採用の理由                                                     |
| ------------------------------ | ---------------------------------------------------------------- |
| Next.js                        | 一覧とフォームだけで足り、SSR/CSR 基盤とビルドサイズが見合わない |
| HTML over the wire（htmx 等）  | 自動更新 1 箇所のために依存を増やさない。素の `fetch` で足りる   |
| CSR フレームワーク（React 等） | 画面は 4 操作のみ。クライアント状態を管理する必要がない          |
| データベース                   | 永続状態を持たない要件（NFR-02）に反する                         |
| 対象側エージェント（自作 API） | 対象ごとに導入が必要になる。既存 SSH で代替できる                |
| ICMP ping による死活確認       | raw socket 権限が必要で、SSH 到達性とも一致しない                |
| Docker コンテナ配備            | 単一バイナリ + systemd hardening で足り、NixOS との統合もよい    |

## 2. 構成

```text
ブラウザ
  │ HTTPS / VPN（Tailscale）
  ▼
リバースプロキシ（Nginx：TLS 終端）
  │ loopback HTTP
  ▼
power-manager（単一バイナリ、専用 system user）
  ├── 管理対象 JSON（起動時 + 明示再読込）
  ├── 環境変数（秘密情報・待受・Origin）
  ├── OpenSSH クライアント ── SSH ──> 管理対象
  └── UDP Magic Packet ────────────> 管理対象 LAN
```

アプリケーションは外向きに 3 種類の通信を行う。loopback での HTTP 待受、UDP ブロードキャスト、SSH/TCP の外向き接続である。内向きの受信はリバースプロキシからの loopback のみを想定する（NFR-04）。管理対象は同一 LAN 上にあり（CON-01）、外部からのアクセスは既存の VPN とリバースプロキシを経由する（CON-05）。

## 3. 実行モデル

### 3.1 起動シーケンス

1. 環境変数を読み、Zod で検証する。1 つでも不正なら終了コード `78`（設定エラー）で終了する（NFR-06, NFR-05）。
2. 管理対象 JSON を読み、検証してメモリへ展開する。失敗時も終了コード `78` で終了する（FR-08, FR-09）。
3. Hono アプリケーションを組み立て、`127.0.0.1:$POWER_MANAGER_PORT` で待受を開始する。
4. 起動完了を構造化ログへ 1 行で出す。

`ssh` の存在確認は起動時に必須とせず、停止操作の実行時に `ssh_unavailable` として検出する。これは起動要件（NFR-06）を環境変数・設定 JSON の検証に限定し、パッケージマネージャが `PATH` を提供する配置（Nix）と、手動配置の両方を許容するためである。

終了コード `78` は NixOS モジュール側で `RestartPreventExitStatus` に指定し、再起動ループを防ぐ（NFR-05）。

### 3.2 プロセス内状態

永続化しない。プロセス再起動で初期化される（NFR-02）。

- 有効な設定（`Server[]`）
- 対象別の実行中フラグ（電源操作の排他）
- 対象別の進行中死活確認 Promise（多重実行の抑止）
- 死活確認の並列度を制御するセマフォ

### 3.3 モジュール構成

| ファイル          | 責務                                                                 |
| ----------------- | -------------------------------------------------------------------- |
| `src/index.ts`    | 環境変数・設定の読込み、起動失敗時の終了コード、HTTP 待受の開始      |
| `src/config.ts`   | 環境変数スキーマ、管理対象 JSON スキーマ、設定ストア（原子的再読込） |
| `src/model.ts`    | ドメイン型（`Server`、`RuntimeConfig`、状態・操作・エラーコード）    |
| `src/services.ts` | WOL 送信、SSH 停止、TCP 死活確認、排他制御と並列度制御               |
| `src/app.ts`      | Hono ルーティング、認証・Origin 検証ミドルウェア、HTML 生成          |

外部依存は `hono` と `zod` のみ。TCP/UDP/子プロセス/パスワード検証は Bun 標準 API を使う。

## 4. HTTP インターフェース

すべてのエンドポイントが認証を要求する（FR-10, SEC-01）。

| メソッド | パス                    | 用途                     | 応答                    |
| -------- | ----------------------- | ------------------------ | ----------------------- |
| `GET`    | `/`                     | 一覧画面（SSR）          | HTML                    |
| `GET`    | `/servers/status`       | 状態表示領域の HTML 断片 | HTML 断片（自動更新用） |
| `POST`   | `/servers/:id/wake`     | 起動                     | `303` で一覧へ          |
| `POST`   | `/servers/:id/shutdown` | 停止                     | `303` で一覧へ          |
| `POST`   | `/reload`               | 設定再読込               | `303` で一覧へ          |

- `/servers/status` は UI 用の内部エンドポイントであり、外部自動化向けの公開 API ではない。応答は `text/html` のみとする。
- 変更操作は `POST` に限定し、`Origin` ヘッダーを `POWER_MANAGER_PUBLIC_ORIGIN` と完全一致で照合する（SEC-03）。詳細は [セキュリティ設計](security.md)。
- 操作結果は Post-Redirect-Get で伝える（FR-07）。`303 See Other` で `/?result=<種別>&server=<id>` へ戻り、画面はクエリパラメータから結果表示を組み立てる。操作の再実行は起きない。

### 4.1 画面生成

`hono/jsx` を使わず、テンプレートリテラルで HTML を組み立てる（依存を減らすため）。可変値は必ず HTML エスケープ関数を通す。

一覧画面は次を含む。

- 操作結果の表示領域（`role="status"`）
- 設定再読込フォーム
- サーバーごとのセクション（表示名、状態、起動フォーム、停止フォーム）

停止フォームは `onsubmit` で `window.confirm()` を呼び、拒否時は送信を中止する（FR-05, SEC-07）。この確認は UI 上の誤操作防止であり、サーバー側の確認状態を保持しない。

### 4.2 自動更新

画面末尾のインラインスクリプトが 15 秒間隔で `/servers/status` を `fetch` し、返却された HTML 断片内の `[id]` 要素を現在の DOM の同名要素と差し替える（FR-02）。

- 同一 ID の要素のみを置換するため、フォームの入力状態を壊さない。
- 応答が `4xx`/`5xx`、またはネットワーク失敗のときは何もしない（次周期で再試行）。
- 断片の要素 ID は `status-<server.id>` とし、ID は設定検証で一意性を担保している（FR-09）。
- スクリプトが無効でも一覧・起動・停止・再読込は動作する（NFR-09）。

## 5. 死活確認の実装

- 各対象の `ssh.host` と `ssh.port` へ TCP 接続し、接続成立で `online`、失敗で `offline` とする（FR-03）。確認結果が未取得の初期状態は `unknown` とする。
- 1 件あたりの上限は 5 秒（NFR-07）。タイムアウトも `offline` として扱う。
- 全対象を並列に確認するが、同時実行数は 8 で固定する。コード上の定数として持ち、環境変数などで外部から変更する設定項目は設けない（NFR-08）。
- 対象 ID ごとに進行中 Promise を保持し、同時要求はその Promise を共有する。複数タブ・手動更新・自動更新が重なっても、同一対象への TCP 接続は 1 本に抑える（NFR-08）。
- 確認完了時に Promise を破棄するため、未完了の確認が次周期に重複登録されることはない。

## 6. 電源操作の実装

### 6.1 起動（WOL）

1. MAC アドレスを 6 バイトに分解し、`0xFF` × 6 + MAC × 16 の 102 バイトを組み立てる。
2. UDP ソケットを ephemeral ポートで開き、`wol.broadcastAddress:wol.port` へ送信する。
3. 送信 API が成功した時点で成功とする（FR-04）。上限 5 秒（NFR-07）。

### 6.2 停止（SSH）

`ssh` を子プロセスとして実行する。シェルを介した文字列連結はせず、引数を配列で渡す。

```text
ssh -i <identityFile>
    -o BatchMode=yes
    -o StrictHostKeyChecking=yes
    -o UserKnownHostsFile=<knownHostsFile>
    -p <ssh.port>
    <ssh.user>@<ssh.host>
    <ssh.shutdownCommand>
```

- `BatchMode=yes` でパスワード入力待ちをさせない。
- ホスト鍵検証を必須にし、`known_hosts` を明示する。
- 停止コマンドは配列の 1 引数として渡し、ローカルシェルで解釈させない。
- 終了コード `0` を成功条件とする（FR-05）。上限 30 秒（NFR-07）。
- `ssh` が見つからない場合は操作せず `ssh_unavailable` として扱う。

### 6.3 排他制御

対象 ID ごとの実行中フラグで電源操作を排他する（FR-06）。実行中の対象への操作は `409 Conflict` 相当として扱い、結果表示では「実行中」と区別する。フラグはメモリ上のみで、プロセス再起動で消える（NFR-02）。管理対象は SSH 接続を受け付ける前提であり（CON-02）、秘密情報は実行時に安全な場所から渡される前提で動作する（CON-06）。

## 7. エラー分類

| コード                  | 発生条件                         | HTTP/表示上の扱い                             |
| ----------------------- | -------------------------------- | --------------------------------------------- |
| `invalid_configuration` | 環境変数・設定 JSON の検証失敗   | 起動中止（終了コード 78）／再読込は旧設定維持 |
| `ssh_unavailable`       | `ssh` 実行ファイルが見つからない | 操作失敗                                      |
| `operation_failed`      | タイムアウト、コマンド異常終了   | 操作失敗                                      |
| `busy`                  | 同一対象の電源操作が実行中       | 拒否（実行中として表示）                      |

内部エラーの詳細はログにのみ出し、画面には結果種別と対象 ID だけを出す（FR-07, SEC-05）。

### 7.1 ログ出力

標準出力・標準エラーへ 1 行 1 JSON の構造化ログを出す。ファイルへは書かない（NFR-10）。

| イベント          | 主なフィールド                              |
| ----------------- | ------------------------------------------- |
| `started`         | `port`                                      |
| `startup_failed`  | `code`（`invalid_configuration`）、`reason` |
| `power_operation` | `serverId`、`operation`、`result`、`code`   |
| `config_reload`   | `result`、`reason`（失敗時）                |

`Authorization`、パスワード、ハッシュ、秘密鍵、停止コマンドの内容、環境変数値は出力しない（SEC-05）。ログの保持期間と保存先はホストのログ収集機構に委ねる。

## 9. 見直し候補

技術選定の再検討時に最初に問うべき点。いずれも本書と実装の変更で完結し、要件定義には影響しない。

| 論点           | 現状                         | 見直しの条件・代替案                                                                               |
| -------------- | ---------------------------- | -------------------------------------------------------------------------------------------------- |
| ランタイム     | Bun                          | Bun 固有 API 依存（UDP、子プロセス、Argon2）が移行コスト。Node.js へ移す場合は該当箇所の置換が必要 |
| 死活確認の意味 | TCP 接続成立                 | SSH デーモン停止＝電源断とみなせない構成では、ping やエージェント方式を検討                        |
| 認証           | HTTP Basic                   | 多要素認証や複数利用者が必要になった時点でセッション方式へ変更                                     |
| WOL の到達範囲 | 単一ブロードキャストアドレス | VLAN 分割やルータ越えが必要になった場合は directed broadcast / リレーを検討                        |
| 停止手段       | SSH + 固定コマンド           | 対象が SSH を持たない場合は、対象側 API または BMC/IPMI 連携を検討                                 |
| 画面方式       | SSR + 素の fetch             | 操作種別が増え画面状態が複雑化した場合に htmx 等を検討                                             |
| 設定の反映     | 明示的な再読込操作           | 変更検知による自動反映が必要になった場合、ファイル監視を追加                                       |
