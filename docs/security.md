# power-manager セキュリティ設計

本書は認証・CSRF 対策・秘密情報の取扱い・実行プロセスの権限を定義する。要件は [要件定義](requirements.md) の `SEC-*`、構成は [アーキテクチャ設計](architecture.md)、配備手順は [運用設計](operations.md) を参照する。

## 1. 脅威と前提

| 脅威                                   | 前提・対策の方針                                                   | 関連要件       |
| -------------------------------------- | ------------------------------------------------------------------ | -------------- |
| インターネットからの直接到達           | loopback 待受 + VPN + TLS 終端リバースプロキシ。直接公開しない     | NFR-04, SEC-02 |
| 認証情報の漏洩による不正操作           | 認証必須、Argon2id ハッシュ、ログ・画面への非出力                  | SEC-01, SEC-05 |
| 他サイトからの誘導による意図しない操作 | `Origin` ヘッダーの完全一致検証、状態変更は `POST` のみ            | SEC-03         |
| 悪意ある入力による設定汚染             | Zod による厳格な検証（未知項目の拒否）、起動時・再読込時の全体検証 | FR-09          |
| 停止操作の誤実行                       | 実行前の確認ダイアログ、対象側の最小権限                           | FR-05, SEC-07  |
| アプリ侵害後の権限昇格                 | 専用非特権ユーザー、systemd hardening、capability 剥奪             | SEC-08         |
| 秘密情報のファイル混入                 | 設定 JSON に秘密情報を置かない。環境変数経由で渡す                 | SEC-04, SEC-09 |

前提として、VPN とリバースプロキシの設定は本アプリケーションの管理外であり、正しく構成されているものとする。アプリケーションは loopback から来るリクエストをリバースプロキシ由来として信頼する。

## 2. 認証

### 2.1 方式

HTTP Basic 認証。単一利用者（NFR-01）に対して実装が最小で、セッションストアを持たない要件（NFR-02）と整合する。

すべてのルートにミドルウェアとして適用する。認証を免除するルートは設けない（FR-10, SEC-01）。

### 2.2 検証手順

1. `Authorization` ヘッダーが `Basic ` で始まることを確認する。
2. Base64 を復号し、最初の `:` でユーザー名とパスワードに分割する。
3. ユーザー名を `POWER_MANAGER_AUTH_USERNAME` と完全一致で比較する。
4. パスワードを `POWER_MANAGER_AUTH_PASSWORD_HASH` に対して Argon2id で検証する。
5. いずれかが失敗したら `401 Unauthorized` と `WWW-Authenticate: Basic realm="power-manager"` を返す。

ユーザー名不一致の場合もパスワード検証と同種の応答を返し、どちらが誤りかを区別しない。

### 2.3 パスワードハッシュ

- 受け付ける形式は Argon2id のみ（`$argon2id$` で始まる文字列）。起動時に形式を検証し、不正なら起動を中止する（NFR-06）。
- アプリケーションはハッシュを生成しない。運用者が Argon2id 対応ツールで生成し、秘密情報ファイルへ設定する。
- ハッシュは検証にのみ使用し、画面・ログ・エラー応答へ出力しない（SEC-05）。

### 2.4 ログアウト

提供しない。Basic 認証ではブラウザが認証情報を保持し続けるため、実効的なログアウトはブラウザ側の操作に依存する。この制約は単一利用者前提で許容する。

## 3. CSRF 対策

### 3.1 方針

状態を変更する操作（起動・停止・再読込）は `POST` のみ受け付ける。各要求の `Origin` ヘッダーが `POWER_MANAGER_PUBLIC_ORIGIN` と完全一致しなければ `403 Forbidden` で拒否する（SEC-03）。

- `Origin` ヘッダーが無い要求も拒否する。
- `Referer` は使用しない（パスやクエリの差異で判定が揺れるため）。
- CSRF トークンは導入しない。同一オリジンのフォーム送信と `fetch` で完結する画面構成のため、Origin 検証で十分と判断する。

### 3.2 `POWER_MANAGER_PUBLIC_ORIGIN`

- 既定は HTTPS URL を要求する。
- ローカル開発に限り、ホスト名が厳密に `localhost` の HTTP URL（ポート指定可）を許可する。
- `127.0.0.1`、`::1`、その他のホスト名では HTTP を許可しない（DNS リバインディング的な誤用と設定ミスを防ぐため）。
- リバースプロキシは外部の `Host` とプロトコル情報を正しく転送し、アプリケーションが見る `Origin` と設定値が一致するようにする。

### 3.3 停止の確認

停止フォームは `onsubmit` で `window.confirm()` を呼び、拒否時は送信を中止する（SEC-07）。これは誤クリック防止の UI であり、サーバー側で「確認済み」状態を保持・署名検証するものではない。停止要求自体の保護は Basic 認証と Origin 検証が担う。

## 4. 秘密情報の取扱い

### 4.1 渡し方

| 秘密情報               | 渡し方                                                | 備考                                   |
| ---------------------- | ----------------------------------------------------- | -------------------------------------- |
| Basic 認証のユーザー名 | 環境変数 `POWER_MANAGER_AUTH_USERNAME`                | 秘密ではないが設定ファイルには置かない |
| Basic 認証のハッシュ   | 環境変数 `POWER_MANAGER_AUTH_PASSWORD_HASH`           | Argon2id 形式                          |
| SSH 秘密鍵             | ファイル + 環境変数 `POWER_MANAGER_SSH_IDENTITY_FILE` | 鍵のパスのみ環境変数で渡す             |

管理対象 JSON には秘密情報を一切含めない（SEC-04, CON-07）。SSH のユーザー名は秘密ではないため設定 JSON に置く。

環境変数は systemd の `EnvironmentFile` から読み込む。アプリケーションはモジュールのオプションとして秘密値を受け取らない。これにより、現在の impure な環境変数ファイルと、将来の `sops-nix` が生成する root 限定ファイルのどちらも同じ方法で扱える（SEC-09）。

### 4.2 ファイルの権限

配備側が次を満たす責任を持つ。モジュールは外部から渡されたファイルの所有者・グループ・モードを変更しない（責務の重複を避けるため）。

- SSH 秘密鍵は `power-manager:power-manager` 所有、モード `0400` または `0600`。
- 環境変数ファイルは systemd が root として読むため、`power-manager` ユーザーが読める必要はない。
- 管理対象 JSON と `known_hosts` は `power-manager` が読めればよい（`0644` 等）。
- いずれも `/home` 配下に置かない（`ProtectHome = true` のため）。

### 4.3 ログとエラー応答

記録してよい: 対象サーバー ID、操作種別、成功・失敗、失敗分類、設定再読込の成否。

記録してはならない: `Authorization` ヘッダー、パスワード、パスワードハッシュ、SSH 秘密鍵、停止コマンドの内容、環境変数の値、内部スタックトレース（画面）。

画面には結果種別と対象 ID のみを出す（FR-07, SEC-05）。内部エラーの詳細は標準エラーへ構造化ログとして出す。

## 5. 停止経路の最小権限

対象サーバー側で、専用公開鍵に対応する秘密鍵による SSH ログインを許可し、次のみをパスワードなしで実行できるよう `sudoers` を設定する。

- 固定の停止コマンド（例: `systemctl poweroff`）

要件:

- 停止コマンドは対象ごとに設定 JSON で与えるが、`sudoers` 側で許可される範囲を超えるコマンドは実行できない。
- `NOPASSWD` を付ける対象は停止コマンドに限定し、汎用のシェル権限を与えない。
- 接続ユーザーは管理専用とし、他の用途と共有しない。

アプリケーション側は `BatchMode=yes`、`StrictHostKeyChecking=yes`、明示的な `known_hosts` で接続し、パスワード入力待ちとホスト鍵検証の迂回を禁止する（SEC-06）。停止コマンドは配列の単一引数として渡し、ローカルシェルで解釈させない。

## 6. 実行プロセスの権限

専用の非 root system user `power-manager` で実行する（SEC-08）。systemd の hardening により次を保証する。

- capability を持たない（`CapabilityBoundingSet = ""`、`AmbientCapabilities = ""`）
- 特権昇格を禁止（`NoNewPrivileges = true`、`RestrictSUIDSGID = true`）
- ファイルシステムは読み取り専用相当（`ProtectSystem = "strict"`、`ProtectHome = true`、`PrivateTmp = true`）
- カーネル・時刻・ホスト名などの変更を禁止
- 名前空間・リアルタイム実行・人格変更を制限
- アドレスファミリを `AF_UNIX` / `AF_INET` / `AF_INET6` に限定

`PrivateNetwork`、`IPAddressDeny`、`SocketBindDeny` は設定しない。loopback での待受と、設定により変化する宛先への WOL・SSH・TCP 接続が必要なためである。

`MemoryDenyWriteExecute` と `SystemCallFilter` は、実行環境（Bun と OpenSSH）で動作確認できた時点で追加を検討する。未検証のまま有効化して起動不能にしない。

具体的な `serviceConfig` は [運用設計](operations.md) に記載する。

## 7. 通信の保護

- クライアントとリバースプロキシ間は TLS（リバースプロキシが終端）。
- リバースプロキシとアプリケーション間は loopback の平文 HTTP。同一ホスト内であり、外部から到達できない。
- Magic Packet は UDP ブロードキャストで、認証も暗号化もない。家庭内 LAN に閉じていることを前提とする。
- SSH はホスト鍵検証を必須とし、平文プロトコルへのフォールバックをしない。

## 8. 要件との対応

| 要件   | 実現箇所                                                     |
| ------ | ------------------------------------------------------------ |
| SEC-01 | 全ルート適用の認証ミドルウェア（2 章）                       |
| SEC-02 | loopback 待受、リバースプロキシでの TLS 終端（7 章, NFR-04） |
| SEC-03 | `POST` 限定 + `Origin` 完全一致検証（3 章）                  |
| SEC-04 | 設定 JSON に秘密情報を置かない（4.1）                        |
| SEC-05 | Argon2id 検証、ログ・画面への非出力（2.3, 4.3）              |
| SEC-06 | SSH オプション固定、`sudoers` の最小権限（5 章）             |
| SEC-07 | 停止前の確認ダイアログ（3.3）                                |
| SEC-08 | 専用ユーザー + systemd hardening（6 章）                     |
| SEC-09 | 環境変数経由の受け渡し（4.1）                                |
