# レビュアー用プロンプト

1 観点につき 1 プロンプト。`{{...}}` を埋めてファイルに保存してから投入する
（引数長の事故防止と再利用のため）。

```bash
cat > /tmp/review-{{TICKET}}/prompt-{{PERSPECTIVE}}.md <<'EOF'
...
EOF
herdr agent prompt {{AGENT}} "$(cat /tmp/review-{{TICKET}}/prompt-{{PERSPECTIVE}}.md)" --wait --timeout 900000
```

## テンプレート

```text
あなたは {{PERSPECTIVE}} のレビュアーです。対象は {{TICKET}} の実装です。

## 最初に読むもの
{{EVIDENCE}} を読んでください。差分・変更ファイル全文・検証済み事実・仕様の該当箇所が
すべて入っています。これを読んだうえで、必要な範囲だけ対象ファイルを直接確認してください。

## 厳守事項
- ツール呼び出しは 20 回まで。超えそうなら現時点の所見で書き切る。
- evidence.md の「検証済み事実」を再検証しない。コマンドの再実行、依存ライブラリの再読込、
  再現実験は禁止。疑わしい点はレポートに 1 行書くだけにする。
- リポジトリ全体の探索、docs の通読、node_modules の掘り下げは禁止。
  evidence.md に無い情報がどうしても必要なら、末尾の「未確認事項」に 1 行で列挙する。
- 書き終えたら推敲・採番整理・体裁修正をしない。そのまま提出する。

## レビュー観点
{{CHECKLIST}}

## 出力形式（この表だけを返す。前置き・総括・謝辞は書かない）

| 重大度 | 場所 | 指摘 | 根拠 | 修正案 |
|---|---|---|---|---|
| MUST | app/foo.ts:42 | … | … | … |

- 重大度は 3 つだけ:
  - MUST: 修正しないと目的を達成できない、または重大な不具合・脆弱性になる
  - NITS: 挙動は変わらないが直した方がよい
  - IMO: 好みの範囲の提案
- 場所は `path:line` 形式。行を特定できなければ `path` のみ。
- 根拠も修正案も 1 行。
- 該当なしなら表の代わりに `指摘なし` とだけ書く。
- 表の後に書いてよいのは `未確認事項:` の行だけ。最大 5 行。
- 全体で 60 行を超えない（MUST が多い場合のみ 80 行まで）。
```

## 観点別チェックリスト

`{{CHECKLIST}}` に差し込む。列挙で閉じ、「など」で開かない。

### コード

```text
以下を1つずつ確認する。
- 可読性: 名前が意図を表しているか、関数が1つのことをしているか、分岐のネストが深すぎないか
- ロジックの正確性: 条件式の境界（以上/超、先頭/末尾）、符号、null/undefined の扱い
- エッジケース: 空配列・空文字・0・負数・同時実行・タイムアウト・部分失敗
- エラーハンドリング: 例外の握り潰し、失敗時の状態整合性、利用者への通知内容
- 重複と漏れ: 同じ判定が複数箇所に散っていないか、既存ユーティリティを使い損ねていないか
門番ではなくメンターとして、なぜ直すべきかを根拠欄に1行で書く。
```

### セキュリティ

```text
このコードを敵の視点で読む。以下を1つずつ攻撃可能性として検討する。
- インジェクション: SQL / シェル / コマンド引数 / パス結合 / テンプレート
- XSS: 生 HTML 挿入、dangerouslySetInnerHTML、URL パラメータの反映
- 認証・認可: 認証を飛ばせる経路、他ユーザーのリソースに触れる経路、権限昇格
- CSRF・セッション: Cookie 属性、SameSite、トークン検証、セッション固定
- 秘密情報: ログ・エラーメッセージ・レスポンスへの漏洩、設定へのハードコード
- 入力検証: 型・長さ・範囲・列挙値の検証漏れ、検証と利用の順序（TOCTOU）
- 依存と設定: 危険なデフォルト、緩い CORS、デバッグ機能の有効化
```

### テスト

```text
以下を1つずつ確認する。
- カバレッジ: 新しい分岐・新しいエラー経路に対応するテストがあるか
- アサーション: テストが実際に何かを検証しているか（落ちないだけのテストになっていないか）
- エッジケース: 境界値・異常系・同時実行・空入力のテストがあるか
- テスト分離: グローバル状態・環境変数・タイマー・ファイルシステムへの依存が後続テストを壊さないか
- 偽陽性: 実装を壊したときに落ちるテストか
- 実行時間: 不要に遅いテスト、実ネットワークや実時間に依存するテスト
```

### アーキテクチャ

```text
以下の設計文書と突き合わせる。
- 参照: {{ARCH_DOC}}
- 技術設計との齟齬: 層の責務、依存方向、公開境界が守られているか
- 集約境界: トランザクション境界、変更の一貫性、他集約への直接参照
- ユビキタス言語: ドメイン用語とコード上の名前が一致しているか、別名が混在していないか
- ドメインロジック漏洩: UI・ルーティング・インフラ層に業務ルールが染み出していないか
- 拡張性: 次に仕様が増えたとき、この構造で耐えられるか
```

### 仕様

```text
以下の要件と突き合わせる。
- 参照: {{SPEC_DOC}} とチケットの受け入れ条件
- 実装漏れ: 要件の各項目に対応する実装があるか
- 過剰実装: 要件に無い挙動が入っていないか（勝手なデフォルト値、勝手な制限）
- 仕様の矛盾: 要件定義・設計文書・実装の3者で食い違いがないか
- データモデルの整合性: 型・必須/任意・既存データとの互換性・マイグレーション要否
- 文言: 利用者向けの文言が要件の表現と一致しているか
```
